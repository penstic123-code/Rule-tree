# 需求树是怎么搭起来的

用途：给想看懂、想改这个项目的人。先讲整体怎么运转，再讲每一部分做什么、为什么这样设计。不需要先懂 Claude Code 的内部机制，用到的地方会解释。

## 一句话

需求树就是项目里 `.claude/rules/ruletree/` 这个文件夹：每个需求一个规则文件，文件开头写着它管哪些文件。Claude Code 自己会在 AI 读写这些文件时加载对应的规则；干活的 AI 照着说明书把新的长期要求记进对应的文件；插件把这个文件夹画成树和导图，所有改动都能撤销。

## 为什么靠 Claude Code 自带的机制

Claude Code 有一种「路径规则」：`.claude/rules/` 下的一份规则文件，开头用 `paths:` 写上它管哪些文件（比如 `DataScience/ch03-*.html`），AI 读写这些文件时，Claude Code 就把这份规则交给 AI。对话被压缩以后、派出去的子 agent 里，它照样生效，会话中途改了规则也会推给 AI。

早期的需求树把一整份 `需求树.md` 编译成这些规则文件，再加一个后台「记录员」读对话、往树里记规则。实测下来，AI 违反规则并没有因此变少，确定的收益只有一条：按文件加载以后，每次收到的规则少了 43–65%。记录员却漏记、挂错需求、把提问当成要求，还占了约四分之一的代码。所以 0.21 起去掉了中间那份总表和记录员：规则文件本身就是树，由干活的 AI 自己维护。

改第 3 章时，管第 3 章的、管数据科学课的、管整个项目的三份规则都会被读到，因为它们管的范围一层包着一层；管 AI 课的规则不会出现。

## 一个规则文件长什么样

```markdown
---
paths:
  - "DataScience/ch01-*.html"
---
# C2.1 第1章 🔨
上级：C2 数据科学课
文档：DataScience/_CHAPTERS.md#第1章
- 开场用霍乱的故事
- 决定：例子先于定义，因为读者是高中生
- 段落可以到 6 行（在本范围内取代 P 的「段落不超过 4 行」）
```

| 部分 | 意思 |
|---|---|
| 文件名 `C2.1-第1章.md` | 编号和标题。层级看编号：C2.1 的上级是 C2，没有点的编号挂在根下 |
| `paths:` | 它管哪些文件。新建的需求默认沿用上级的范围 |
| 标题行 | 编号、标题、状态（✅ 完成、🔨 进行中、⏳ 待做、❓ 待定） |
| `上级：` | 写给 AI 看的，程序不靠它定层级 |
| `文档：` | 背景文档，AI 动手前先读；`路径#节名` 只挂一节 |
| 列表项 | 规则。用户拍板的以「决定：」开头；下级推翻上级时末尾写取代说明 |

另外两个特殊文件：`_root.md` 是全项目都要守的规则（不写 `paths:`，每次都加载）；`_guide.md` 是说明书，告诉 AI 这个文件夹怎么读、新要求记到哪里，由工具生成，不要手改。

## 各部分做什么

| 部分 | 什么时候跑 | 做什么 | 代码 |
|---|---|---|---|
| 树 | 每次读写 | 把一组规则文件读成一棵树；面板和体检的每个修改都走同一个入口 | `src/tree.js` |
| 存储 | 每次改规则 | 加锁写文件；每条改动记下改动文件的前后两版，撤销时按行反着打补丁（之后别人在同一个文件里的改动留着） | `src/store.js` |
| 说明书 | 启用时、版本变了时 | 写 `_guide.md`：怎么读、怎么记、「决定：」不许自己推翻、冲突时以后写的为准 | `src/guide.js` |
| hook（Claude Code 在特定时刻调用的小程序） | AI 改文件后、Claude Code 加载规则文件时，都在后台跑 | 记下 AI 在改哪个需求；AI 改了规则文件就记一条改动（来源「AI」）；记下每个会话加载了哪些规则、多少字 | `hooks/hook.js` |
| 体检 | 你点「体检」时 | 程序先查：规则送不到、没写范围、下级超出上级、文档或节不在、规则太多、编号重复；意思一样的规则直接删一条。再调用一次模型找重复、矛盾、过时的，能改的直接改，碰「决定：」的写进报告让你定。规则一条没变就不调用模型 | `src/checkup.js` |
| 规则分组 | 体检时 | 规则多的需求按话题分组，只改面板显示 | `src/categories.js` |
| 升级 | 打开旧版项目时 | 把旧的 `需求树.md` 拆成规则文件，旧 hook 换成新的，原文件挪进 `.ruletree/legacy/` | `src/migrate.js` |
| 界面 | 一直 | 侧栏、导图、详情面板；在编辑器里改规则文件、保存，记成「你」的改动 | `extension.js`、`media/` |
| 命令行 | 你运行时 | 启用、停用、看树、体检 | `bin/ruletree.js` |

Codex 的支持（`src/targets/`、`hooks/codex-hook.js`）改到一半，还没接进命令行和插件。

## 文件放在哪

| 文件 | 内容 | 要不要提交进 git |
|---|---|---|
| `.claude/rules/ruletree/` | 需求树本身 | 要。worktree 和队友自动就有 |
| `.ruletree/` | 改动记录、快照、活动、上下文用量、体检报告、旧版留底 | 不要（已加进 `.gitignore`） |
| `~/.ruletree/runtime/` | hook 程序的副本；插件升级时自动更新 | 不在项目里 |

## 改动是怎么记下来、怎么撤销的

`.ruletree/snapshot.json` 存着每个规则文件上次见到的内容。谁改了文件，谁就对一下快照，把前后两版记成一条改动：

| 谁改的 | 谁来记 | 来源 |
|---|---|---|
| 面板上点的 | 插件，写文件的同时 | 你 |
| 编辑器里手改、保存 | 插件，保存时 | 你 |
| AI 用编辑工具改 | PostToolUse hook | AI |
| 体检 | 体检，写文件的同时 | 体检 |
| 命令行、git、别的途径 | 插件刷新时（改完 5 秒以后，免得抢在 hook 前面） | 其他 |

撤销时，每个文件找出那次改动的那几行：还原样在，就换回去；那几行后来被删了、改了，就跳过。所以撤销一条旧改动，不会把之后别人在同一个文件里加的规则一起冲掉。

## 关键的设计决定

| 决定 | 为什么 |
|---|---|
| 规则文件就是需求树，不再从一份总表编译 | 两份东西迟早一份改了一份没改；规则文件进 git 以后，worktree 和队友不用再抄 |
| 不要记录员，干活的 AI 自己记 | 记录员漏记 14–20%、会挂错需求、把提问记成要求，每轮还要多跑 8–15 秒。干活的 AI 手上已经加载着它在改的需求的文件，记到那里最准 |
| 只靠原生按路径加载，不补送 | 实测补送的 5 次全是重复：原生加载 0–2 分钟内都到了。讨论某个需求、还没碰它的文件时，说明书让 AI 先读那个需求的文件 |
| 改动直接生效，不逐条请你确认，但每条都能撤销 | 逐条确认太累；全不确认又怕错 |
| 层级看编号 | 文件之间没有先后，编号是唯一稳定的线索；「上级：」一行只给 AI 看 |
| 规则一句话，细节放文档 | 规则每次都要读，所以要短；文档只在需要时读 |
| hook 只读 Claude Code 公开的字段，不读对话记录文件 | 对话记录的格式没有公开，随时可能变 |

## 命令行

```bash
node bin/ruletree.js init    [目录]          # 启用：装 hook、忽略 .ruletree/；旧版的 需求树.md 拆成规则文件，没有就按文件夹建第一批需求
node bin/ruletree.js disable [目录]          # 停用：去掉 hook（规则文件留着）
node bin/ruletree.js tree    [目录]          # 打印整棵树
node bin/ruletree.js rules   C2.1 [目录]     # 某个需求实际要守的规则（含上级的）
node bin/ruletree.js check   [目录]          # 只用程序检查，不改文件
node bin/ruletree.js checkup [目录]          # 体检（--no-model 不调用模型）
```
