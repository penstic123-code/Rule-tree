# 设计：信息架构、代码地图、自动体检（0.13）

> 2026-10-26 重构以后，这份笔记里的代码地图、记录员、AI 初始化和重新整理、自动检查、信息架构评分都已删掉，现在的设计见 [architecture.md](architecture.md)。这里留作当时为什么这样设计的记录。

给想改需求树代码的人看的设计笔记。文中的 Vibelearning 是作者的六门互动网页课程项目，猪猪进城记是作者的 Godot 游戏，都是用来实测的真实项目。

用途：说明 AI 干活要的信息分别放在哪、什么时候到 AI 手上，以及 0.13 为此加的东西。接手改这几块之前先读。

## 一、目标

用户要的三件事：AI 不重复造轮子、不写冲突的代码、干活时信息齐全（规则、背景、代码结构、决定的来由）。同时用户不想逐条拍板：能自动处理的直接做，记录在案、可以撤销，只有真拿不准的才问。

## 二、信息放在哪

| 层 | 放什么 | 什么时候到 AI 手上 |
|---|---|---|
| CLAUDE.md / AGENTS.md | 入口：项目是什么、东西在哪、少数全局硬规则 | 每次全文加载，所以越短越好 |
| 需求树规则 | 短而具体、以后都要照做的要求 | 改到对应文件时（原生路径规则） |
| 决定（以「决定：」开头的规则） | 用户拍板的做法和理由：选 A 不选 B，因为…… | 同上；AI 要推翻先问用户 |
| 文档（`> 文档：`） | 长篇规范、进度、章节表、经验 | 改到对应文件时，提醒先读 |
| 代码地图 | 这块已有的文件、对外函数/类/信号、它依赖的公共模块 | 改到对应文件时；全项目的公共模块每次加载 |
| `reqtree who <名字>` | 某个函数、类、信号在哪定义、谁在用 | AI 需要时自己运行 |
| 自动记忆 | 只放和项目内容无关的事 | Claude Code 自己管 |

## 三、需求树怎么组织，规则最少

一条规则放在「刚好覆盖它适用的全部文件」的节点上。需求不必只按内容分（课程、模块），也可以按文件类型横切：

```
# P 项目                        ← 全局（越少越好）
## W 写作   > 文件：*/ch*.html  ← 横切：所有课的正文；挂通用写作规范
## C2 某课  > 文件：C2/**       ← 内容：这门课
### C2.W 写作 > 文件：C2/ch*.html ← 这门课自己的写法
```

- 一个文件命中几个需求，几份规则都加载（Claude 原生本来如此；0.13 起补送 hook 也这样）。
- 说法冲突时，文件范围更窄的需求优先（编译进总目录的说明）。
- 本课的写作规则只有一两条时放在课程节点上就行。
- 0.16 删掉的「按话题自动拆子需求」只拿一个需求的规则分堆，拆出的子需求没有更窄的文件，省不了加载。0.19 改成整棵树「先定结构，再挂规则」（第七节）：按项目在做的事一次分好层级，子需求落到自己的文件夹、数据文件上，规则再挂到管它的那个。

## 四、动手原则（编进总目录，`principles` 配置可关）

1. 遇到 bug，先找根因：规则互相矛盾、架构不合理、系统之间冲突的，先解决这些，不在表面打补丁。
2. 写新东西之前依次问：真需要吗 → 项目里已经有了吗（看代码地图、运行 `reqtree who`）→ 标准库或平台自带的能做吗 → 已装的依赖能做吗 → 最后才写最少能用的代码。校验、数据安全、无障碍不省。（借鉴 ponytail 的「阶梯」）
3. 「决定：」开头的规则是用户定下的，要推翻先问。

2026-10-25（0.18.0）曾把 ponytail 原文（MIT，提交 09c434a，英文约 3,200 字）编成只在代码文件上加载的规则。同一天去掉，缺的几条并进总目录里写代码的那句（改动做全、调用方和测试一起改、非平凡逻辑留小测试、校验和防丢数据等不省、做完说清没做的和风险），常驻多约 80 字。原因：一半和动手原则重复；实测在空项目里新建第一个代码文件时，按路径加载的规则跟着写文件的结果才到，文件已经写完了；初始化还把 `src/ponytail.md` 挂成了文档，体检把里面的句子搬进树、从原文删掉（之后加了 `docs.isProgramData`：程序运行时读的 .md 不算文档）。

### 信息架构自动整理（`src/structure.js`，体检时，不调用模型）

2026-10-25 在 Vibelearning 实测发现：教育课没有需求（改它只拿到通用写作规则，它自己的说明文档 AI 不知道）；记忆里存着几门课的进度。原因是需求树原来是被动的：用户说一句记一句，不主动维护结构。体检加了一步：

1. 没有专门需求的内容文件夹（最上一层、60 天内改过、至少 3 个文件、不全是 .md、不是工具素材备份）→ 新建需求，名字取第一层说明文档标题「：」前那段，挂上文件夹和说明文档。「专门」指文件对应以这个文件夹开头；`*/ch*.html` 这种横切的不算。编号跟着有专门文件夹的兄弟的字母走，取最大号加一，不补空位（空号可能是删掉的需求，改动记录还指着它）。
2. 没挂文档的需求，挂上自己文件夹第一层的说明文档（最多 3 份，规则、进度、章节类优先）。
3. 按章的子需求（标题或文件看得出第几章）挂上级文档里只讲这一章的那一节（`_CHAPTERS.md#第 1 章`）。实测 AI 会按行号只读挂的那一节。
4. 下级需求的文档里，和上级文档逐字重复的列表项删掉（上级的文档提示改下级文件时也会加载）。只看列表项：普通段落常是讲文档自己的话，试跑时三份规范文档各有一句「本文节号沿用原来的 CLAUDE.md」，不能当重复删。平级之间不动。
5. 模型判为某需求经验或进度的记忆，原文接到那个需求挂的文档末尾（进度类文档优先），删掉记忆。

都只改需求树，或者原样搬、原样删，不改写文档内容（10-22 搬家实验里模型改写时把「互动上限 5」改成了 4）。每项都经 `settle` → `Q.decide`：直接做、可撤销，撤销过的不再做。不自动拆大文档：实测目录加行号已经让 AI 只读相关的节。

## 五、代码地图（`src/codemap.js`）

为什么不用现成的：aider 的 repo map 和 graphify 都不支持 GDScript（2026-10 查过：aider 的语言表里 GDScript 只有语法检查；graphify 依赖的 14 种 tree-sitter 语法里没有它），而用户的游戏项目是 Godot。正则就能读出够用的结构，不用装 tree-sitter，也不调用模型。

- 文件清单：`git ls-files -co --exclude-standard`（跟着 .gitignore），不是 git 仓库就遍历目录并跳过依赖、构建产物；跳过 `.min.js`、超过 300 KB 的文件。
- 每种语言一个读法（`ADAPTERS`）：
  - GDScript：`class_name`、`extends`、`signal`、顶层 `func`（不以 `_` 开头的算对外）、文件开头 `##` 说明；`project.godot` 的自动加载单例；`X.信号.emit/connect` 记成发出 / 监听；`preload/load("res://…")` 和 `.tscn` 里挂的脚本记成引用。
  - JS/TS：`function`、`class`、`export`、`module.exports`、顶层 `const x = (…) =>`；`require/import` 和 HTML 的 `<script src>`、`<link href>` 记成引用。
  - Python：顶层 `def`、`class`，模块文档字符串；`import`。
  - 其他语言：`func/fn/def/function/class/struct/interface` 开头的行。
- 排序（借鉴 aider）：一个文件被多少个别的文件引用（按路径引用，加上按名字引用，名字只认够长、全项目只有一两处定义的）。
- 输出：每个最下一层的需求一份 `.reqtree/map/<ID>.md`（0.20 起不自动加载：总目录里一句话告诉 AI 在哪，想知道时自己读；原来按路径整份加载，实测每次多占约 4000 字却没看出效果，见 test-log 第十六节；git worktree 里各抄一份）：这块最常被引用的文件和一句说明、对外的名字，以及这块依赖的外部公共模块。按文件类型横切的需求（glob 都以 * 开头）不出地图，免得把各块的东西混在一起。全局的 `_map.md`：Godot 自动加载单例；需求树还没按内容分块（没有任何地图）时再加上全项目最常被引用的模块。每份有字数上限。
- 更新：记录员每轮结束后（这一轮改过文件、离上次超过 2 分钟）在后台重建；内容没变不重写，免得触发「文件已变更」通知。命令行 `reqtree map` 立刻重建。

### 和需求树融合（0.20）

0.19 以前地图只照着需求的范围列文件，范围划错了地图跟着错（猪猪进城记「行人与交通」的地图里列着 `shop_hours.gd`、`shop_crew.gd` 这些店铺代码），地图算出的依赖关系也从没帮需求树划过范围。现在三处用它，都不多调模型：

| 用在哪 | 怎么用 |
|---|---|
| 整理时划需求（`init.codeOutline`） | 给模型看被 3 个以上文件用的代码：一句用途、被几个文件用、主要来自哪些文件夹；用的人分散的标「公共」。重新整理时再列出现在可能挂错的文件 |
| 体检查范围（`codemap.placement`） | 一个文件归范围覆盖它的最深的按内容分的需求；用它的文件八成以上在另一个顶层需求里（至少 3 个），它自己却不归那里，算挂错。5 个以上算「该重新整理」的迹象，报告里列出来 |
| 过时规则、记录员挂规则 | 规则里写的类名、函数名（反引号里的、`snake_case`、`EventBus` 这种驼峰）代码里一个都找不到，算过时的证据；记录员给只提到名字的规则按定义它的文件挂（`.reqtree/codemap.json` 的 `owners`） |

两条边界（用户 2026-10-25 定）：依赖关系只说明谁调用谁，说明不了谁属于哪件事。被 3 个以上顶层需求的文件用的是公共模块（`Tuning`、`EventBus`、`Clock`），不判挂错、不记进 `owners`（「数值都从 Tuning 读」管的是所有用它的代码，不是 `tuning.gd` 那一块）。测试、工具脚本只是辅助，不算「用它的那一块」：不去掉的话，被测得多的模块全成了「该归开发工具」。

## 六、体检自动化

照记录员的做法：**直接生效、记进「最近改动」、可以撤销；只有拿不准的才问**（问的时候默认做法已经写进去，回答别的选项会先撤销它）。

| 发现 | 处理 |
|---|---|
| 同一需求里重复的规则 | 删前面那条（原有） |
| 下级重复了上级已有的规则 | 删下级那条（新） |
| 规则冲突 | 模型给出默认做法和 `sure`；有把握就直接改，没把握才问 |
| 几个需求都有的同一条 | 模型建议提到共同上级，同上 |
| 文档、CLAUDE.md 里和树重复的 | 从文档里删掉那一行（先备份，可撤销）；表格行、找不准的不删，只写进报告 |
| 文档里该搬进树的规则 | 加进树，再从文档里删掉那一行 |
| 规则多的需求、根上规则太多（24 条以上）、规则挂在永远送不到的需求上、挂错的代码文件多（5 个以上） | 先自动重新整理一次（第七节，Sonnet 一次，同一棵树自动只做一次，撤销了不再自动做）；之后面板上照样按话题分组显示（0.20 起模型只回规则序号，不抄原文：猪猪进城记 285 条规则光抄原文就超过 300 秒，体检超时） |
| 改同一个文件时一起送到、不在一条上下级链上的两条（「写作」和某门课） | 程序按真实文件算哪些需求会一起送到，挑出话题相近的（字面重合度 ≥ 0.35，最多 25 对），模型判重复 / 冲突 / 不相干；重复、冲突的删一条（`src/rulecheck.js`） |
| 过时的规则 | 程序先找证据：提到的文件、路径找不到（不分大小写），提到的类名、函数名代码里找不到（0.20），读着像进度；模型确认了才处理：没用了的删掉，进度搬进这个需求挂的文档末尾。不按时间长短删 |
| 两份文档说法矛盾（0.20） | 同一批里的两份文档，模型给出两边的原文和照对方改好的文字；按谁后改的（有没提交的改动按修改时间，否则按最后一次提交时间）改先改的那份（`doc_replace`）；一小时内都改过、分不出先后的不动，写进报告。分批时同一块（文档挂的需求所在的顶层需求）的文档尽量装进同一批；改过的文档带上同一条上下级链上挂的、这次本来跳过的旧文档（最多 3 份、各取第一段）一起看，旧文档只拿来比 clash，不从里面找规则。两块不相干的内容的文档之间还是比不到 |
| 能写成检查的规则（0.20） | 模型挑出一行就能判断违反的规则，给 glob 和正则，程序核对后存进 `.reqtree/checks.json`，AI 改完文件时 hook 查（第十一节） |
| 记忆 | 同上：有把握的直接做（删记忆前备份） |

文档和记忆的改动是「文件操作」（`doc_remove` / `memory_remove`），和树的改动记成同一条，撤销时一起还原。

## 七、用 AI 初始化（`src/init.js`，0.17）

起因：用户的游戏项目一直停在空模板（项目名 / 第一个需求 / 子需求），记录员记下的 58 条规则全挂在根上；0.16 的「按文件夹生成」只替换一字没改的模板，体检又不建结构，所以一直没变成能用的树。

| 什么时候跑 | 新建需求树；插件启动时发现树还没真正初始化过（模板标题还在，或开头还是按文件夹生成的那句说明，哪怕已经记了规则；一天最多自动试一次）；点体检时发现树是这样 |
|---|---|
| 读什么 | 文件夹概览（三层、带文件数）、说明文档清单、README、CLAUDE.md / AGENTS.md 全文和各节字数、最近 40 条提交和改到的文件夹、树里已经记下的规则 |
| 模型（Sonnet，一次） | 按「要做的事」分需求（不按文件夹）、文件范围、状态、每个需求挂哪几份说明文档（最多 4 份）、已有规则各分到哪个需求、CLAUDE.md 里哪几节大段参考资料搬成单独的文档 |
| 程序把关 | 文件范围只留真能匹配到文件的；文档要真存在、不是测试样例；拆的节要找得到、够长（400 字以上）、入口文档本身要长（3000 字以上）、目标路径在项目里且不存在；规则按编号分，没分到的留在根上，一条不丢、原文不改 |
| 写入 | 直接生效，记成一条改动（来源「初始化」）。需求树、拆出的新文档、拆过的 CLAUDE.md 都是整份写（`doc_write`），写前整份备份；撤销时整份放回（`doc_put_back`），放回前把当时的内容再备份一份 |
| 之后 | 接着体检文档和记忆：把 CLAUDE.md 和挂上的文档里写成规则的句子搬进树（体检原有的逻辑） |
| 失败 | 没装 Claude、超时、模型给的一个需求都用不上：留下按文件夹生成的树，提示之后体检会再试 |

搬到新文档的节一个字不改写，原处只留标题和一行「见某文档」：AI 改写会悄悄改掉意思，合并重复交给之后的体检。

### 重新整理：先定结构，再挂规则（0.19）

起因：猪猪进城记初始化后只有一层，一个需求挂 41 条规则，改城市里任何一个文件 AI 都收到这 41 条；树一旦不是模板样子，就没有任何步骤再动它的结构。用户的要求：「能不能直接就知道怎么拆分需求，然后再去挂规则」「三层不够」。

- 和初始化是同一条路（`init.js` 的 `write`）：模型看项目（文件夹到四层、文档的用途和标题、README、提交）、现有的树（只作参考）和每条规则现在挂在哪，先定结构，再给每条规则一个编号的去处。
- 深浅看内容：一个需求预计 12 条以上规则、或者里面几块各有各的做法，就往下拆；只剩几条、再拆也说不出不同做法就停。最多 5 层（`##` 到 `######`）。
- 程序把关：文件范围要匹配到真实文件，子需求的范围必须在上级范围里（不在的那条 glob 去掉）；规则原文不改，每条只放一处，模型漏掉的放回原来那个需求（新树里还有同号的），否则放根上；原来挂的文档都要还挂着（没挂上的挂到接了原需求最多规则的新需求上）；同一件事沿用原编号；最顶上的标题和说明原样留着。
- 整份写入，记成一条改动（来源「整理」），一键撤销。等模型时别的会话记下的规则补回去。
- 什么时候做：命令「需求树：重新整理（AI）」、`reqtree reorganize`；体检看到迹象（某个需求自己挂了 12 条以上、或有规则的需求永远送不到）时自动做一次（`.reqtree/reorganized.json`，撤销了不再自动做）。
- 实测（猪猪进城记，只读试跑，Sonnet 85 秒）：11 个需求 → 38 个，两层；285 条规则一条不少；改一个文件平均收到的规则 83.8 → 62 条（剩下的大头是根上 52 条协作、派工、通用代码规范）；城市下面那批「店里怎么布置」的规则挪到了「店铺布置与设施」。数据见 test-log 第十五节。
- 修根节点（0.20）：上面剩下的 52 条里有 9 条只管代码、4 条只管文档，改任何文件却都会送到。根源是提示词写着「通用的代码和文档规范留在根上」，把「对全项目都适用」和「改任何文件都要看到」混成了一件事。现在：根上只留不管改什么文件都要守的（协作、派工、沟通、范围和优先级）；只管某一类文件的通用做法挂到按文件类型的需求（代码、文档分开建，如「代码规范」`**/*.gd`）。顶层需求之间的范围尽量不重叠；代码按依赖分（第五节）。

## 八、体检里两类「说法不一样」怎么判（0.17）

| 情况 | 处理 |
|---|---|
| 记忆说的是一条例外（「云除外」） | 不算冲突，按记忆处理时在旁边加一条「例外：……」，不替换主规则。2026-10-25 实测旧版把「光照只有一条规则……」整条换成了「云保留预设色，作为例外」 |
| 记忆和树冲突，树里那条是用户的话定下的（记录员记的、或用户在面板上改的） | 比时间：记忆的修改时间和那条规则定下的时间，新的为准，不问。体检、初始化搬进来的规则没有「定下的时间」，照模型判断 |
| 文档挂在某个需求下，说法和这个需求自己的规则冲突 | 按需求树改文档里那几个字（`doc_replace`，表格行也行，原文全文只出现一次才改），可撤销；改不成的写进报告。全项目的规范文档和某个需求说法不同，是那个需求的例外，不改 |

## 九、重复体检要快：只查变了的（0.19）

0.18 的体检每次都把整棵树交给模型找冲突、分组；文档和记忆已经按指纹跳过，规则这一批却每回都跑，重复体检照样要几分钟。

- `.reqtree/checkup-seen.json` 里加 `rules`：上次查过的每条规则（需求 ID + 规则文字的指纹）。
- 规则一条都没变：不排规则那一批，文档和记忆也没变时整个体检不调用模型（`checkPlan().calls` 为 0），几秒结束。
- 变了：提示词里列出新加、改过的规则，模型只看它们和跟它们有关的（同一需求、上下级、一起送到的）；一起送到的候选对、过时的候选也只取牵涉到这几条的；分组只给规则变了的、和还没分过组的需求重分。
- 「全部重查」照旧全看。

## 十一、能写成检查的规则（`src/checks.js`，0.20）

规则写进树，AI 也会忘；「不留调试输出」「不用某个说法」这类一行就看得出的，AI 改完文件马上被点出来最管用。

- 哪些规则能查：体检查规则的那次调用里，模型从新加、改过的规则里挑（第一次是全部），给 glob 和 JavaScript 正则（匹配到的那一行就可能违反），最多 10 条。要看效果、要跑程序、要看整篇、要靠理解的不做。
- 程序核对：规则在树里；正则合法、不匹配空串；glob 在这个需求的范围里匹配得到文件；拿现有文件试一遍，超过 1 秒的不要（可能回溯爆炸），一半以上的现有文件都「违反」的不要（多半是误报，或者这条本来没人照做，查了只会刷屏）。存进 `.reqtree/checks.json`，按规则的指纹对应：规则改了、删了，检查跟着失效。
- 什么时候查：Claude 的 PostToolUse（Edit / Write / MultiEdit 写进去的文字）、Codex 的 apply_patch（加进去的行）。只查这次写进去的，不查整份文件（原来就有的不反复提）。可能违反就作为附加上下文告诉 AI（后台 hook 的附加上下文在下一次请求模型时送到），说明是按写法查的、不一定准；不拦、不改文件。
